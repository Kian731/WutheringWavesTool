# 交接說明 — 鳴潮攻略站（本機靜態網站）

> 寫給下一個接手的 AI / 開發者。原本由 Claude Code 在 2026-08～10 建置。
> 專案根目錄：`D:\_個人資料\wuthering`　·　非 git 專案（沒有版本控制，改動前請自行備份）

---

## 0. 先讀這三件事

1. **這是純靜態網站，沒有建置步驟。** 直接用瀏覽器開 `index.html` 就能跑。
   資料用 `<script src="data/*.js">` 載入、掛在 `window.WW_*` 上，**刻意不用 `fetch`**，
   這樣 `file://` 協定也能運作（使用者常直接點開檔案，不一定會起伺服器）。
   → 不要把資料改成 JSON + fetch，會讓使用者的日常用法直接壞掉。

2. **使用者要的是「自助更新」。** 遊戲會一直出新角色／武器／聲骸，
   使用者按一下 `更新資料.bat` 就要能把新內容抓進來，不需要再找人改程式。
   → 任何新功能都要想「新角色上架時這塊會自己長出來嗎？」

3. **使用者對「看起來對但其實錯」的資料非常敏感，而且抓得很準。**
   他抓到過：主聲骸配置錯、素材圖示錯置、技能養成算法不合理。
   → 寧可少顯示，不要顯示錯的。沒把握的資料標示來源或留白。

## 3. 資料管線（tools/）

`更新資料.bat` → `tools/update.mjs` → 依序跑 17 個步驟。**順序有相依性，不要亂調。**

```
scrape → pageimgs2 → build → fetch-images → supp → fetch-images → kuro-fill
→ sonata-data → plan-data
→ merge-dupe-mats → mats-audit → fix-families → item-icons → item-icons-kuro
→ sync-char-mat-icons
→ kuro-recommend → classify
```

每一支在做什麼，`README.md` 的「手動執行（進階）」那一節有逐條說明。

### 資料來源

| 來源 | 負責 |
|---|---|
| 鳴潮 BWIKI（`wiki.biligame.com/wutheringwaves/api.php`，MediaWiki API） | 主要：基本資料、技能、共鳴鏈、武器、聲骸、突破素材 |
| 庫街區官方 WIKI（`api.kurobbs.com`，headers 要 `wiki_type: 9` + `source: h5`） | 技能／突破素材補齊、**配裝推薦（以官方為準）** |
| wuthering.gg | 補 BWIKI 沒上傳的立繪／圖示 |
| mc.appfeng.com（鳴潮助手） | 聲骸套裝合鳴效果 |

簡體原文用 **OpenCC**（`cn`→`tw`）轉繁，另有 `FIX` 覆寫表修「里/裡」誤轉（維裡奈→維里奈、相裡要→相里要）。

### 這個環境的網路限制（重要）

- **`curl` 跑不通**（sandbox 擋掉，exit 6）。
- **Node 加 `dangerouslyDisableSandbox: true` 可以連外網** —— 所有抓資料都走這條。
- 內建瀏覽器只能連 localhost，連不到外部網站。
- BWIKI 的 `Special:FilePath` 有反爬，會回傳 JS 頁面。
  **一定要走 `prop=imageinfo&iiprop=url` 拿 patchwiki CDN 網址**，下載後還要驗魔術位元組。
- BWIKI 前面有 EdgeOne WAF 會限速：偵測到回應不是 JSON 就要退避重試（5～60 秒）。

## 4. 踩過的坑（別再踩一次）

### 4.1 `data/ascension.js` 不能做字串手術 ⚠️ 最嚴重

`"mats":` 這個鍵在檔案裡出現 **299 次**（每個技能分支節點都有一個）。
我用 `indexOf('"mats":')` 找「素材登錄表」，結果抓到第一個分支節點的陣列，寫下去就把資料改壞了。

→ **一律用 `tools/asc-io.mjs` 的 `loadAsc()` / `saveAsc()`**：整包解析 → 改 → 整包寫回，
寫入前會檢查必要欄位、分支節點格式、序列化後筆數，不對就中止。
`data/characters.js` 同理（`sync-char-mat-icons.mjs` 裡有安全寫法可參考）。

### 4.2 圖片檔名絕對不能用遞增編號

舊做法存成 `p_001.png`、`p_002.png`…，編號跑一次遞增一次。
但每次執行登錄到的素材集合會變，**同一個編號在不同次代表不同素材**；
下載迴圈又有「檔案已存在就跳過」，舊圖就留下來配到別人身上。
結果 `p_011`~`p_018` 和 `p_025`~`p_032` 是八組位元組相同的檔案（剛好差 14 號）。

→ **檔名必須由素材名稱決定**：`m_<md5(名稱).slice(0,12)>.png`，跟執行順序無關。
→ 圖示來源只接受**完全對應**的：BWIKI 檔名一字不差的 `道具 <簡體名>.png`，
   或庫街區突破材料表裡「圖片和名稱在同一段 HTML」抓下來的配對。對不上就留白。
→ `mats-audit.mjs` 每次會做內容雜湊比對，兩個素材撞同一張圖就一起清掉。

### 4.3 兩邊來源的引號寫法不同會造成重複登錄

BWIKI 用 `「」`、庫街區用 `“”`，同一個素材被登錄成兩種，養成計劃就把它算兩次。
已知三組：`“來生”`／`「來生」`、`“金羊毛”`／`「金羊毛」`、`中級囈語聲核`／`中頻囈語聲核`（後者是錯字）。
→ `merge-dupe-mats.mjs` 每次會自動合併，新來源若又冒出新寫法它也會抓到。

### 4.4 合成家族有兩種命名型態

- **共同後綴**：低頻／中頻／高頻／全頻 ＋ `○○聲核`（原本只認得這種）
- **共同前綴**：`聲律`種核→萌芽→新葉→花蕾、`海蝕嵌合體`210→226→235→239

兩種都要認，判定條件一樣嚴格：3～4 個成員、各自第一次出現的突破階層互不相同。
（`海蝕嵌合體210` 這種帶數字的名字是 BWIKI 原始寫法，不是抓壞的，不要「修正」。）

### 4.5 主聲骸＝放在首位的那個，不是 COST 最高的

一度用「COST 最高」推斷主聲骸，是錯的。
正確依據是庫街區的「**聲骸首位推薦**」／技能文字裡的「在首位裝配該聲骸技能時」。
例：穗穗的主聲骸是 COST3 的封庭械囿，不是 COST4 的千傀重樓。

比對聲骸名稱時的陷阱：
- 「角」會誤中「角色」→ 要求長度 ≥2 且限縮在該分頁的聲骸集合內
- 「無冠者」會蓋掉「夢魘·無冠者」→ 比對結束位置，長的優先
- 重跑會殘留上次的值 → `kuro-recommend.mjs` 會先從 `data/backup/` 還原再覆蓋

### 4.6 .bat 檔必須是 ASCII + CRLF

系統碼頁是 950（Big5），UTF-8 的 .bat 會變亂碼而且跑不起來。
→ 兩個 .bat 保持純 ASCII、CRLF、無 BOM，中文訊息一律移到 Node 裡輸出。

### 4.7 其他

- `build.mjs` 會先寫 `gaps.json` 再讓 `supp.mjs` 讀它合併，不是覆蓋
  （之前 supp 會自我抵銷，立繪從 56 掉到 46）
- BWIKI 的素材總量偶有錯（忌炎高頻聲核寫 4，正解 12）→ `build.mjs` 會以 4/12/12/4 正規化並記錄
- 瀏覽器 console 的錯誤訊息會跨頁殘留，**驗證有沒有修好要開新分頁**
- `setSelectionRange` 不支援 `<input type=number>`，會丟例外（已包 try/catch）

## 5. 關鍵設計決策（不要未經討論就推翻）

| 決策 | 原因 |
|---|---|
| 資料用 `<script>` 掛 `window.WW_*`，不用 fetch | 要能在 `file://` 下運作 |
| 練度只存 localStorage，不做後端 | 使用者要的是本機工具；跨裝置用匯出代碼手動搬 |
| 不支援用遊戲 UID 匯入練度 | **查證過做不到**：鳴潮沒有角色櫥窗，庫街區 API 需要帳號存取令牌，沒有公開查詢。使用者已接受「批次設定（不碰帳號）」這條路 |
| 新角色自動補值會標「系統推估」 | 官方資料還沒出時先給參考值，但要讓使用者知道這不可信 |
| 養成計劃的技能預設讀「我的角色」的各技能實際等級 | 使用者明確要求過，不要退回成「五個技能同一個等級」 |
| 素材表用並列小卡（同合成線縱向、不同線橫向） | 使用者明確要求過，一列一個素材要滑很久 |

### ⚠️ 安全界線（使用者已同意，不要越線）

曾經評估過「用庫街區 token 匯入真實練度」這條路。結論是：
**token 等同帳號存取權，只能留在使用者自己的機器上，絕對不可以外傳（包括貼進對話），我方也不需要看到。**
如果之後重新討論這個方向，這條界線依然有效。

## 8. 怎麼驗證改動

沒有自動化測試。實務上用這套流程：

1. 起本機伺服器（專案有 `.claude/launch.json`，或 `node .claude/serve.js` → `localhost:8777`）
2. 用瀏覽器開對應頁面，**優先用 DOM 查詢驗證而不是截圖**（截圖在這環境常失敗）
3. 檢查 console 有沒有錯誤 —— **一定要開新分頁**，舊分頁會殘留先前的錯誤
4. 數字類改動要**對帳**：例如逐列加總 vs 頁首總計 vs 卡片標題總計，三者要一致
5. 手機版用 375px 檢查：不截斷、不橫向溢出
6. 測完清掉 localStorage 的測試資料

資料類改動的對帳腳本可以參考這次用過的寫法（在 `conversation.md` 裡搜尋「對帳」）。
